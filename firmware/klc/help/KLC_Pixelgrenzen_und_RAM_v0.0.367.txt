KLC Pixelgrenzen und RAM-Auslegung
Firmwarestand: 0.0.367
Absicherung eingefuehrt: 0.0.366

Verbindliche Profilwerte der aktuellen beiden Boardprofile
----------------------------------------------------------
Pro physischem Ausgang:
- 0 bis 800 Pixel: unbedenklicher Bereich
- 801 bis 1200 Pixel: zulaessiger Warnbereich
- ab 1201 Pixel: abgelehnt

Aktive Gesamtpixel:
- 0 bis 3200 Pixel: unbedenklicher Bereich
- 3201 bis 6000 Pixel: zulaessiger Warnbereich
- ab 6001 Pixel: abgelehnt

Speichergrenzen:
- dynamisches LED-Pufferbudget: 128 KiB
- zusaetzliche Mindestreserve fuer das restliche System: 64 KiB

Diese Werte sind eine bewusst konservative KLC-Sicherheitsauslegung. Sie sind
keine allgemeine oder exakt vorgeschriebene WLED-Konstante und keine Behauptung,
dass auf jeder Hardware unter jeder Laufzeitlast exakt 64 KiB garantiert frei
bleiben.

Reale Pufferberechnung
----------------------
Das aktuelle PIO+DMA-Backend reserviert je aktivem Ausgang gleichzeitig:
1. Renderpuffer: uint32_t je Ausgabepixel
2. DMA-/Ausgabepuffer: uint32_t je Ausgabepixel
3. Blackout-/Tail-Bereich: 64 zusaetzliche Pixel in beiden Puffern

Berechnung je aktivem Ausgang:
  (konfigurierte Pixel + 64 Tail-Pixel) * (4 Byte Render + 4 Byte DMA)

Damit gelten 8 Byte je Pixelposition der gemeinsamen Pufferrepraesentation.
RGB und RGBW belegen in diesem Backend gleich viel Puffer-RAM, weil beide als
uint32_t-Ausgabewort gespeichert werden. Die Farbkanalzahl veraendert daher
nicht die Pixeloffsets oder Kettenlaenge.

Beispiel 1200 Pixel:
  (1200 + 64) * 8 = 10.112 Byte pro Ausgang

Budget und Reserve
------------------
Das feste 128-KiB-Budget begrenzt den maximalen Anteil fuer alle gleichzeitig
dynamisch reservierten LED-Puffer. Die 64-KiB-Mindestreserve wird zusaetzlich
fuer WebUI, Netzwerk/WLAN, BAOS, JSON-Verarbeitung, Szenen und Laufzeitspitzen
verlangt und nicht vom 128-KiB-Pufferbudget abgezogen.

Laufzeitpruefung
----------------
Vor der LED-Allokation werden:
- aktive Gesamtpixel,
- geschaetzter Pufferbedarf,
- festes Pufferbudget,
- Mindestreserve und
- soweit auf Arduino-Pico/RP2350 verfuegbar der freie Heap
geprueft.

Die Plattformabfrage rp2040.getFreeHeap() liefert eine obere Grenze des frei
allokierbaren Heaps. Verwaltungsaufwand und Fragmentierung koennen dazu fuehren,
dass eine einzelne reale Allokation kleiner ausfallen muss. Deshalb bleiben die
Einzelallokationspruefungen zwingend bestehen.

Nach der Allokation wird der freie Heap erneut gemessen. Unterschreitet er die
Mindestreserve, werden die LED-Puffer sicher freigegeben und die Ausgabe nicht
aktiviert. Ist eine belastbare Heapabfrage in einem Hosttest oder fremden Build
nicht vorhanden, gelten weiterhin das statische Budget und die geprueften
Einzelallokationen; die Diagnose darf dann keine gemessene Garantie anzeigen.

Allokationsfehler
-----------------
Schlaegt nach einem bereits reservierten Teilpuffer die naechste Allokation fehl:
- werden alle Teilpuffer dieses Ausgangs freigegeben,
- werden deren Zeiger auf nullptr gesetzt,
- wird nur der betroffene Ausgang deaktiviert,
- wird Diagnosefehler 1701 gesetzt,
- koennen unabhaengige weitere Ausgaenge weiter initialisiert werden.

WebUI/API-Diagnose
------------------
Die Ausgangs-API liefert die profilbezogenen Grenzwerte sowie:
- aktive Gesamtpixel,
- geschaetzten LED-Pufferbedarf,
- 128-KiB-Pufferbudget,
- 64-KiB-Mindestreserve,
- freien Heap vor/nach Allokation, soweit messbar,
- Status safe / warning / rejected / allocation_failed beziehungsweise
  reserve_rejected/reserve_failed,
- ID eines von einer Allokation betroffenen Ausgangs.

Import und Migration
--------------------
Ein fehlendes altes Feld darf weiter ueber Defaults/Migration ergaenzt werden.
Ein vorhandenes, aber negatives, syntaktisch ungueltiges, ueberlaufendes oder
fachlich zu grosses Pixel-Feld lehnt dagegen den gesamten Import mit
Ausgangsindex, Wert und Maximum ab. Es gibt kein Clamping und keine stille
Default-Ersetzung. Der Bereich 801..1200 bleibt gueltig und wird mit einer
klaren Leistungs-/RAM-Warnung uebernommen.
